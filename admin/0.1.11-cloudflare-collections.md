# Admin Android 0.1.11: sincronización manual de colecciones

Base: `fix/admin-0.1.10-remove-thetvdb`, commit `4e9074e1b1cfbe87d7e2345e6557ef2abc5f2cdf`, versión 0.1.10 / 11. La rama base se conserva. La confirmación de funcionamiento físico de 0.1.10 procede del propietario. Objetivo: `feature/admin-0.1.11-cloudflare-collections`, `0.1.11-diagnostico` / 12, `ar.com.miflix.admin`.

## Contrato y alcance

La referencia obligatoria es el JavaScript del Worker de producción proporcionado por el propietario (`miflix-worker-colecciones.js`, versión de archivo 1, 14.764 bytes), conservado íntegro exclusivamente como fixture en `admin/tools/fixtures/worker-production-collections.mjs`. No se usa ni modifica `feature/worker-safe-collections`. No hay cambios de Worker, clientes, Windows, credenciales remotas ni esquema compartido.

`GET` y `PUT /admin/colecciones`, ambos con el Bearer administrativo existente. Cuerpo exacto: `{format:"miflix-collections",version:1,colecciones:[...]}`. El PUT reemplaza el conjunto completo, no películas. Se comprueba `ok:true`, cantidad y `updated_at` válido. No se envían ETag, If-Match ni claves de idempotencia.

Se reutiliza la validación local existente (máximo 2 MiB por documento), agregando el rango de enteros seguros de JavaScript y la regla URL de `validateCollections`. Es un límite cliente conservador; el Worker admite hasta 5 MiB para la solicitud y para el catálogo final. Si el remoto supera el límite cliente, se rechaza su importación y no se permite publicar sobre una comparación incompleta.

## Flujo

Colecciones → **Sincronizar colecciones con Cloudflare** → **Consultar y comparar con Cloudflare**. No hay consultas al abrir la pantalla ni sincronización automática. La comparación muestra IDs, nombres, altas/cambios/bajas y valores actuales/propuestos de cada campo, incluidos integrantes, imágenes y orden. Los campos desconocidos de cada colección se conservan.

**Revisar publicación** abre el resumen. Todo reemplazo exige esta confirmación; cambios/eliminaciones remotos exigen además una casilla explícita. Un arreglo vacío exige otra casilla específica incluso cuando el conjunto remoto leído está vacío. Los borradores no forman parte del envío.

Al confirmar, se comprueba que la copia local y la configuración no cambiaron, se repite el GET y se rechaza un cambio remoto visible antes de enviar PUT. Se conserva íntegramente `collections-state.json` al publicar, tanto en éxito como en fallo. La confirmación informa la fecha del servidor; una lectura inmediata puede seguir mostrando la versión anterior.

La recuperación es independiente: elegir IDs remotos → comparar → confirmar. Se agregan o reemplazan únicamente las colecciones seleccionadas; ninguna no seleccionada se elimina. Se usa `CollectionRepository.replaceApproved` y su respaldo anterior/AtomicFile. Un borrador activo impide esta recuperación con un mensaje específico; no se borra automáticamente. Se puede revertir desde **Restaurar estado anterior de colecciones**. Consultar o cancelar no escribe datos.

## Publicación normal y consistencia

Admin 0.1.10 comparaba el catálogo completo para detectar conflictos: cambiar solamente colecciones habría bloqueado la siguiente edición de película. `CatalogCollections` excluye únicamente `colecciones` y `colecciones_version` de esa comparación y del cuerpo de `PUT /admin/catalogo`. Sigue detectando cambios audiovisuales y campos desconocidos ajenos a colecciones. La base y el espejo local conservan las colecciones leídas al publicar/actualizar. El Worker vigente es quien preserva el conjunto remoto en la publicación normal.

No hay garantías de serialización: entre GET y PUT otro administrador puede publicar; KV puede devolver datos antiguos y el PUT del Worker sigue siendo lectura-modificación-escritura sin transacción. Usar un solo administrador/dispositivo a la vez. El reintento es manual. Si una respuesta se pierde, no se asume fracaso remoto ni se repite el PUT automáticamente: consultar y comparar otra vez. Interrumpir una publicación no puede deshacer una solicitud ya recibida.

No se migra ni cambia el formato de colecciones/caché/respaldo. No se cambia ninguna referencia Telegram, fecha de incorporación, ID audiovisual, temporada ni episodio. La retirada de TheTVDB, TMDB/TVmaze selectivo, las colecciones manuales/TMDB y el detector de sagas se conservan. La consulta remota no crea películas ni integrantes nuevos en el catálogo.

## Comprobaciones reproducibles

Ejecutar con JDK 17, SDK 34 y Gradle 8.2:

```sh
./gradlew :admin:clean :admin:testDebugUnitTest :admin:testReleaseUnitTest :admin:lintDebug :admin:lintRelease :admin:assembleDebug :admin:assembleRelease
node --test admin/tools/test_collections_worker.mjs
node --test admin/tools/test_retired_worker.mjs
python3 admin/tools/test_collection_schema.py
```

Las pruebas Gradle generan `admin/build/collections-worker-contract.json` con las proyecciones reales de Android y datos sintéticos. El harness Node ejecuta el Worker íntegro contra KV simulado: publicación/lectura, reemplazo, vacío, autenticación, formato, límites de tamaño, error de almacenamiento, preservación audiovisual/campos desconocidos y publicación normal posterior. No emula propagación ni convierte KV en almacenamiento atómico. Los tests Kotlin comprueban el flujo de confirmaciones, persistencia, cancelación, recuperación, errores de conexión/HTTP, ACK y regresiones de publicación.

## Instalación y primera publicación de Depredador

1. Exportar el respaldo de colecciones y conservar también el respaldo del catálogo. No desinstalar ni borrar datos.
2. Instalar la APK release firmada como **Actualización** sobre 0.1.10. La identidad requerida es SHA-256 `C5125975AC14BCD11FFB402158BA112F0E72C92B87DF268B56B77F810CAFD49B`; no crear otra clave.
3. En Colecciones verificar Depredador, sus cinco integrantes, imágenes y orden. Guardar cualquier borrador que deba publicarse; el envío incluye todas las colecciones guardadas, no solo la seleccionada visualmente.
4. Abrir sincronización y consultar. Si el remoto está vacío, debe mostrarse Depredador como alta y ninguna eliminación. Si existen otras colecciones remotas, recuperarlas primero si deben conservarse o revisar explícitamente su eliminación: publicar reemplaza todo el conjunto.
5. Revisar y confirmar una sola vez. Esperar la confirmación del servidor y volver a consultar manualmente tras la propagación de KV. No repetir publicaciones rápidas ante una lectura antigua.
6. Revisar los cinco IDs, imágenes y orden recuperados. Luego realizar una edición legítima mínima de una película y sincronizar por el procedimiento habitual; confirmar que la colección sigue en el remoto.
