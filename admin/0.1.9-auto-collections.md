## Detección implementada

Inicio → Colecciones → **Detectar sagas en mi catálogo** → **Analizar / reanudar con caché**.

1. Toma una copia del catálogo cargado. Filtra `tipo=pelicula` con TMDB ID entero positivo hasta Int32; acepta también su representación decimal de texto. Cero, fracciones, exponentes, IDs fuera de rango y ausencias se cuentan como sin ID válido. No busca ni asigna IDs por título.
2. Consulta cada TMDB ID distinto una vez con `GET /3/movie/{id}?language=es-AR`. Exige identidad correcta y `belongs_to_collection` presente; `null` explícito significa sin colección. Campo ausente/inválido es error, no una pertenencia inventada.
3. Agrupa pertenencias y consulta una vez `GET /3/collection/{id}?language=es-AR`. Verifica ID, nombre y partes válidas sin IDs duplicados. Solo se usan colecciones oficiales; no se infiere un universo Marvel/DC.
4. Cruza partes con películas actuales mediante ID TMDB exacto. Dos versiones locales con el mismo ID se muestran ambiguas y se excluyen del lote. Coincidencias de nombre/año no se usan durante el análisis masivo; el editor 0.1.8 permite la revisión explícita individual.
5. Muestra propuesta, póster, presentes, ausentes por ID, total TMDB, referencias seguras, estado y actuales. Todas las propuestas empiezan sin seleccionar. Ignorar solo oculta en la revisión actual y no se interpreta como borrado ni exclusión permanente.
6. El usuario selecciona una o varias propuestas, revisa el resumen y confirma **guardado local**. Consultar, revisar el resumen o cancelarlo no guarda colecciones ni altera películas.

Concurrencia deliberadamente limitada a **una solicitud activa** y separación de 300 ms antes de cada petición. HTTP con timeout de llamada 25 s, sin redirecciones y lectura acotada a 5 MiB; hasta tres intentos por fallo transitorio (conexión, HTTP 5xx o 429). Espera progresiva 1/2 s y `max(espera, Retry-After)`; admite segundos o fecha HTTP. Si la espera supera 60 s o se agotan los reintentos de 429, se interrumpe el análisis y no se siguen enviando peticiones para otras películas. Se conserva una pausa global durable para futuras reanudaciones; borrar la caché no la elude. 401/403 interrumpen inmediatamente. Otros errores permanentes no se reintentan.

No se fija un límite de TMDB como si fuera una garantía contractual: su documentación permite variación y exige respetar 429. Se conserva el token/relay existente; no se añade otra credencial. El relay fuente recuperado permite `/movie/{id}`, pero no `/collection/{id}`; en esa configuración se necesita el **TMDB Bearer Token local opcional ya existente**, como en 0.1.8. La prueba física del usuario confirma que la consulta de colecciones funcionó en su teléfono, pero no revela aquí sus credenciales ni permite presuponer un despliegue distinto.

## Caché, progreso y cancelación

`collections-tmdb-cache.json`, AtomicFile independiente, solo contiene pertenencias (incluido `null`), detalles públicos de TMDB y marcas de tiempo/pausa. Nunca contiene tokens ni películas del catálogo. TTL de siete días, hasta 10000 entradas aproximadamente y 6 MiB; se expulsan las más antiguas. Fallos no se cachean como éxito. Se conserva cada respuesta exitosa antes de continuar, permitiendo reutilización después de cancelar o reiniciar. Un fallo de escritura de caché se informa como consulta fallida y no modifica colecciones. La opción de reconsultar sin caché requiere confirmación y no borra catálogo/borradores/colecciones.

El progreso distingue total de películas, analizadas (incluidas las consultas fallidas), pendientes, sin ID válido, consultas fallidas, sagas detectadas y respuestas reutilizadas. Las consultas de detalle fallidas también se suman; no todas las fallas representan películas distintas. Terminado sin fallos significa que se consultaron todos los IDs válidos, no que se resolvieron películas sin ID ni ambigüedades. Esas limitaciones permanecen visibles.

Cancelar cancela el cliente HTTP y la tarea; un contador de generación descarta respuestas tardías. Salir de la sección cancela la tarea. No hay servicio de segundo plano. Los resultados visibles son una revisión temporal; la caché permite reconstruirla. Los resultados parciales no se anuncian como detección completa.

## Actualización sin duplicar Depredador

Una colección con el mismo `tmdb_collection_id` se reconoce aunque tenga otro nombre o imágenes personalizadas. La aprobación en lote **solo añade al final IDs exactos, únicos y nuevos**. No cambia ID interno de colección, nombre, descripción, origen previo, imágenes, orden de colección/integrantes, visibilidad, campos desconocidos ni integrantes manuales/ausentes. No elimina películas ni referencias. Una saga completa no es seleccionable para un lote sin cambios.

Si existen varias colecciones con el mismo TMDB ID, se muestra conflicto y se excluyen de la aprobación automática. Una colección manual sin ese ID nunca se fusiona por parecido de nombre. La opción **Revisar en editor / elegir campos** reutiliza la comparación y selector visual existentes; todos los campos e integrantes empiezan desmarcados al abrir desde detección. Se puede elegir una versión ambigua o datos/imágenes alternativos explícitamente. El guardado sigue exigiendo vista previa y confirmación 0.1.8.

Las nuevas colecciones de un lote aprobado reciben nombre, descripción no vacía e imágenes principales válidas de TMDB, origen/ID TMDB y referencias seguras. La pantalla informa esto antes de seleccionar. Para una elección diferente se usa el editor. Un solo integrante seguro basta para ofrecer una saga; no se inventan películas ausentes. La fecha y las referencias Telegram pertenecen a películas y ni siquiera forman parte del objeto guardado de colección.

El resumen congela el plan aprobado. Antes de confirmar se comprueba que catálogo y lista de colecciones sigan iguales a la base revisada; un cambio obliga a revisar otra vez. El lote se guarda atómicamente con un respaldo anterior; no hay guardados parciales por saga.

El Worker completo fuente recuperado conserva campos si llegan en el objeto completo, pero el PUT reemplaza toda la raíz. No valida colecciones, no tiene PATCH, ETag/If-Match, respaldo previo, revisión ni endpoint exclusivo. La prueba de un escritor antiguo sin colecciones reproduce su eliminación. Un escritor obsoleto con una copia vieja reproduce su sobrescritura. Añadir una revisión comparada con un GET de KV tampoco es atómico.

La documentación oficial de Cloudflare confirma consistencia eventual y ausencia de transacciones KV; límites KV 25 MiB/valor y una escritura por segundo/clave, mientras este Worker impone 5 MiB/cuerpo. Un mutex de isolate no resuelve concurrencia global. Se comparó almacenamiento unificado con colecciones separadas y composición pública. Se recomienda un coordinador transaccional con operaciones independientes y respuesta pública unificada; un Durable Object SQLite es una opción en la plataforma existente, disponible bajo límites del plan gratuito, **no creado ni implementado aquí**. Requiere conocer despliegue, bindings, permisos y ensayar migración con un KV separado antes de autorizar producción.

Las fuentes Windows 1.13.6 y los lectores Mobile 0.9.13/TV 0.1.13 ya auditados se vuelven a probar con datos sintéticos. Windows preserva raíz en los caminos conocidos; eso no protege contra otros escritores históricos. Los clientes leen `items` correctamente con `colecciones_version:1` y `colecciones`; no se modifica ni habilita su representación visual. Los fixtures de parsers están solo en tests de Admin. No se conoce ni verifica el Worker desplegado; no se consultó su catálogo. El informe anterior conserva los SHAs exactos de fuentes y ZIPs.

La política TheTVDB continúa bloqueando la publicación audiovisual restringida. **Detectar/guardar/exportar colecciones TMDB/manuales es independiente y no queda bloqueado por tener TheTVDB local.** La futura operación de colecciones debe enviar solo objetos/referencias; no copiar registros restringidos. Esto no se simula eliminando procedencia ni recortando metadatos. La publicación normal mantiene su protección anterior.
