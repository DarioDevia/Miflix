## Decisión de publicación: local en esta etapa

**Las colecciones se guardan en un archivo separado del catálogo. No se agregan al JSON que se sincroniza ni se eliminan del JSON remoto para publicar.** El catálogo habitual sigue usando exactamente sus funciones anteriores y no marca pendientes por guardar una colección. Un archivo de colecciones corrupto/desconocido bloquea solo la edición de colecciones, no películas, series, anime ni su sincronización normal.

Aunque el Worker fuente, Windows 1.13.6 y Admin Android conocido conservan propiedades adicionales en los caminos probados, no se verificó el Worker desplegado ni el conjunto completo de administradores/executables instalados. La app por sí sola no puede impedir que un escritor antiguo reconstruya posteriormente una raíz sin `colecciones`. Se requiere una garantía del lado servidor o un protocolo de compatibilidad para ese caso, que aquí no se desplegó. Se eligió la opción autorizada de persistencia local y exportación, en vez de presumir cumplidas las seis condiciones de publicación.

No se introduce un bloqueo general por colecciones locales. La protección TheTVDB **ya existente** sí sigue bloqueando catálogos que tengan esos metadatos restringidos. La nueva sección no la elude ni la resuelve. Separar con seguridad los campos restringidos requeriría una proyección publicable y una capa local por campo, con bases históricas verificables, conflictos, migración de estados 0.1.7 y atribución/permisos en clientes. El respaldo de un nivel no basta para reconstruir cualquier historial después de múltiples importaciones. No se recortan campos ni se quita procedencia para simular una solución.

## Arquitectura mínima y almacenamiento

- `CollectionRules`: contrato, validación, guardado por ID, integrantes, orden y cruces. Solo referencias a títulos, sin copias de registros.
- `CollectionRepository` + `CollectionFileStore`: `AtomicFile` independiente en `filesDir/collections-state.json`. Reutilizan `StateStore`; no cambian la envoltura del catálogo ni las credenciales cifradas.
- `TmdbCollections` / `CollectionProvider`: HTTP TMDB usando `HttpMetadata` existente; búsqueda, detalle y alternativas de imágenes.
- `CollectionController`: estados de pantalla, borrador durable, consulta cancelable, comparación y aplicación explícita; una tarea IO con generación que descarta resultados tardíos.
- `CollectionScreens`: listado, manual, importación/personalización, comparación, imágenes, vista previa y documentos Android para exportar/restaurar.

`collections-state.json` tiene `storage_version:1`, `data` con el formato exportable, `draft`/`editing_id` opcionales y `backup` con el estado anterior. Cada guardado, eliminación o restauración válida conserva un nivel anterior; la próxima operación lo reemplaza. No es un historial ilimitado. Los errores de escritura atómica mantienen el estado anterior. Cancelar una consulta conserva el borrador. Salir de Colecciones conserva su borrador; descartarlo requiere confirmación. El archivo con versión desconocida se mantiene sin sobrescribir hasta una restauración explícita y validada.

El respaldo exportado usa el selector de documentos de Android: no requiere permisos generales ni acceso al almacenamiento de otras apps. Incluye solo colecciones guardadas, no borradores, títulos completos, rutas de reproducción, referencias Telegram, configuración ni credenciales. Puede revelar nombres e IDs de las colecciones del usuario; debe conservarse privadamente. El catálogo debe respaldarse por separado: exportar colecciones no es un respaldo del catálogo completo.

Restaurar muestra previamente cuántas colecciones contiene el archivo y solicita confirmación antes de reemplazar datos y borrador. Se valida formato/versión/tipos, IDs duplicados, URLs, origen, orden e integrantes. Se rechaza un JSON de catálogo completo como si fuera un respaldo de colecciones. Se mantienen referencias a IDs ausentes temporalmente. Una restauración sobre archivo corrupto/desconocido es explícita; no se presenta como recuperado un estado que no puede interpretarse.

## Contrato documentado para próximas etapas

Archivo formal: `admin/colecciones.schema.json` (JSON Schema 2020-12). Formato exportable:

```json
{
  "format": "miflix-collections",
  "version": 1,
  "colecciones": [
    {
      "id": "col-UUID-estable",
      "nombre": "Mundo Marvel",
      "descripcion": "Selección personal",
      "origen": "manual",
      "poster_url": "https://example.invalid/poster.jpg",
      "backdrop_url": null,
      "orden": 0,
      "visible": true,
      "titulos": ["ID-REAL-MIFLIX-1", "ID-REAL-MIFLIX-2"]
    }
  ]
}
```

IDs de colección nuevos: `col-` + UUID, independientes del nombre. Editar no cambia ese ID. Orígenes: `manual` o `tmdb`; este último requiere `tmdb_collection_id` entero positivo. Una colección importada personalizada conserva ese origen/ID como procedencia; posteriores consultas no restauran datos automáticamente. `idioma_tmdb` opcional identifica el idioma solicitado en la última selección explícita de esos datos, no un idioma detectado automáticamente. No se traduce texto mediante IA.

`titulos` conserva el orden definido por el usuario. Un título puede estar en varias colecciones. Adiciones solo aceptan IDs existentes en el catálogo consultado; referencias ya guardadas que estén ausentes no se purgan. Doble selección no duplica. Quitar o borrar colecciones no modifica ningún `item`, temporada, episodio, enlace, reproducción ni fecha. `orden` (0 a 1000000) define el orden de presentación de colecciones; `visible` se conserva para clientes futuros y no activa nada en clientes actuales.

Se admiten hasta 1000 colecciones, 10000 referencias por colección y 2 MB por archivo exportable. Nombre hasta 200 caracteres, descripción hasta 12000, URLs hasta 2000. El contrato permite propiedades desconocidas y las conserva en lectura/edición/restauración de la versión conocida. Hay validaciones adicionales de unicidad de IDs de colección y de URL HTTPS sin userinfo en Kotlin, porque JSON Schema no expresa por sí solo todas las invariantes. Cambios de formato o versión se rechazan, no se reinterpretan.

El futuro catálogo remoto puede incorporar de forma aditiva `colecciones_version:1` y `colecciones` con estos mismos objetos, sin tocar `items`; esta versión no produce ese catálogo ni cambia `schema_version` o `catalogo.schema.json`. Antes de habilitarlo se debe garantizar preservación por todos los escritores, límites conjuntos del JSON del Worker, respaldo remoto recuperable y resolución de conflictos. El formato actual evita reescribir los objetos de colección en Mobile/TV/Windows después.

## TMDB: endpoints, idioma e imágenes

Documentación oficial consultada:

- https://developer.themoviedb.org/reference/search-collection
- https://developer.themoviedb.org/reference/collection-details
- https://developer.themoviedb.org/reference/collection-images
- https://developer.themoviedb.org/docs/image-basics
- https://developer.themoviedb.org/docs/faq
- https://www.themoviedb.org/about/logos-attribution

Se usa `GET /3/search/collection?query=…&language=es-AR&include_adult=false&page=…`, con paginación explícita; un ID positivo introducido consulta el detalle directamente. Detalle: `GET /3/collection/{id}?language=es-AR`. Alternativas de imágenes: `GET /3/collection/{id}/images` sin filtro de idioma para ofrecer las disponibles. No se usa `belongs_to_collection` para construir universos completos. Marvel/DC se crean manualmente o combinando una saga con títulos propios, nunca por una supuesta lista automática universal.

Idioma inicial `es-AR`. Si falta descripción, la pantalla lo informa y conserva la actual. El usuario puede elegir `en-US` explícitamente y volver a consultar; la comparación muestra el idioma y requiere seleccionar campos. Admin no hace otra llamada de fallback ni sobrescribe silenciosamente nombres, descripciones o imágenes manuales. TMDB puede devolver su texto original cuando no tiene traducción: la interfaz advierte esa posibilidad y etiqueta el idioma como solicitado, no como detección lingüística.

El cruce oficial solo considera `tipo=pelicula` y `tmdb_id` igual. Varias versiones con el mismo TMDB ID se muestran como ambiguas. Sin ID, un nombre normalizado igual y año igual solo propone una coincidencia dudosa, que necesita selección manual. Un TMDB ID distinto no se reemplaza por parecido de nombre. Cada integrante, incluso el de ID exacto, queda sin seleccionar hasta que el usuario lo marque. Películas ausentes se enumeran y no se crean.

El póster/fondo se eligen visualmente, con idioma e imagen reducida. Se muestran alternativas devueltas por TMDB, con filtro Todos/es/en/sin idioma; otros idiomas siguen visibles en Todos con su etiqueta. Las miniaturas usan w342/w780, y se guardan URLs w500/w1280 para póster/fondo. No se descargan originales gigantes ni se incrustan bytes en JSON. El editor también permite URL HTTPS personalizada, validada sin userinfo. Los dominios conocidos de TheTVDB se rechazan también como URL manual; no se usa su proveedor ni sus imágenes en este sistema. El origen/licencia de una imagen alojada en otro dominio debe verificarse por el administrador. Si no hay imágenes, se conserva lo actual y se ofrece URL manual.

**Relay actual:** el Worker fuente accesible no permite búsqueda/detalle/imágenes de colecciones. Para usar TMDB en esta etapa se reutiliza el **TMDB Bearer Token local opcional** de Configuración del servidor. No se agregó una segunda configuración ni se trasladaron credenciales. Si no está configurado y el relay rechaza la ruta, se muestra un mensaje específico. Un relay futuro compatible también podrá atender las rutas, pero aquí no se modificó ni desplegó el Worker. Autenticación rechazada, timeout, JSON incompleto y límites de solicitudes se notifican sin aplicar datos ni mostrar secretos.

No había credenciales TMDB reales disponibles en Work: los endpoints nuevos se probaron con MockWebServer. No se afirma una importación real autenticada con la cuenta del propietario. La validación física debe comprobar esa conexión.

TMDB se atribuye en búsqueda, comparación y selección de imágenes, con logo oficial, enlace y aviso de no certificación. El recurso `tmdb_logo.xml` conserva el path, gradiente y proporción del SVG aprobado: https://www.themoviedb.org/assets/v4/logos/v2/blue_short-8e7b30f73a4020692ccca9c88bafe5dcb6f8a62a4c6bc55cd9ba82bb2cd95f6c.svg . No usa una dependencia SVG ni imágenes de TheTVDB. El uso comercial necesita el acuerdo pertinente con TMDB; esta entrega no certifica licencia comercial de MiFlix.
