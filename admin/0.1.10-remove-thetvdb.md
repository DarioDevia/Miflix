# Admin Android 0.1.10-diagnostico / 11 — Retirada de TheTVDB

31/10/2026. Actualización correctiva de Admin Android. Sin lectura ni escritura del catálogo de producción en Work. Sin cambios en Worker, Mobile, TV o Windows. Sin uso de Durable Objects ni sincronización remota de colecciones.

## Base comprobada

Se verificó el inventario remoto de ramas antes de editar. Base real: `feature/admin-0.1.9-auto-collections`, commit `e5a52976e6ff909401fa8516bcffd23f88d08e1c`, árbol `80a9b4d110e37baf5f44d6bf1c3a1150d7c60e87`, `0.1.9-diagnostico` / código 10 / `ar.com.miflix.admin`. ## Causa exacta

`MetadataPublicationPolicy.containsTvdb` recorría recursivamente TODO el documento y consideraba restringido cualquier objeto con `fuente` o `provider` TheTVDB o `publicacion_bloqueada:true`. `AdminRepository.publish` rechazaba el catálogo antes del PUT; `CatalogRules.publicCopy` repetía el rechazo. Una sola sinopsis importada y guardada bastaba para impedir publicar todas las películas, series y anime. Las credenciales válidas no levantaban ese control.

`MetadataRecovery.apply` registraba por campo la procedencia en `fuentes_metadata.recuperacion_selectiva`, con claves `title/season/campo`, `N/season/campo` y `N/E/campo`. Esos registros sí permiten identificar qué se importó. El `metadata_undo` guarda únicamente el antes/después de la última recuperación, no un historial completo. No se puede inventar el original de un campo si ese respaldo o la base remota no lo demuestran.

El propietario confirma que no publicó metadatos TheTVDB. Esto justifica conservar como referencia independiente la base descargada del servidor cuando no contiene procedencia retirada para ese campo; no prueba qué hay en su teléfono. Work no tuvo acceso a esos archivos privados: la inspección y limpieza de sus registros concretos ocurren al instalar/abrir la APK.

## Componentes retirados

- `TvdbApi.kt`: login, token, renovación, HTTP y pruebas de conexión.
- `TvdbRecoveryProvider.kt`: búsqueda, traducciones, temporadas, episodios y adaptación.
- `TvdbConfig.kt`: edición, cifrado/descifrado y guardado específico de API Key/PIN.
- Opciones TheTVDB de `RecoverySourceMenu`, búsqueda, comparación, atribución como proveedor activo, mensajes de bloqueo y configuración exclusiva.
- Estado/token/credenciales TheTVDB de `AdminViewModel`; solo se admiten TMDB y TVmaze en recuperación selectiva. Un plan histórico TheTVDB no puede volver a aplicarse aunque se le pase una aceptación de licencia.
- Se sustituyó la política de rechazo global por una proyección de saneamiento (`MetadataPublicationPolicy.projection`). Su nombre permanece como límite central de serialización; ya no rechaza todo el catálogo por una marca histórica.

No había dependencias Gradle exclusivas de TheTVDB. No se actualizaron dependencias ni se reemplazó la recuperación selectiva general. TMDB, TVmaze, atribución CC BY-SA, AniList existente, imágenes, selección de campos y reversión de recuperaciones vigentes siguen usando sus componentes previos.

## Migración local y publicación segura

La compatibilidad histórica reside en `RetiredMetadata`, no en un proveedor activo. Se ejecuta al leer el estado, antes de los commits del repositorio y como defensa pura al producir JSON público. Es idempotente y no consulta servicios externos.

1. Lee `catalog`, `draft`, `base` y `metadata_undo`. Identifica procedencia por campo, grupos generales, marcadores de objetos y URLs conocidas de imágenes del proveedor retirado. Los checkpoints y respaldos históricos se conservan; no forman parte del JSON público.
2. Antes de cambiar un valor persistido, guarda el estado original completo en `noBackupFilesDir/retired-metadata/<SHA256>.json`. El hash corresponde a los bytes UTF-8 exactos del respaldo. AtomicFile confirma la escritura; un archivo existente se verifica y nunca se sobrescribe con otro contenido. Los respaldos históricos no se eliminan ni sustituyen.
3. Solo sanea el catálogo activo y el borrador. No borra títulos, temporadas ni episodios. IDs, numeración, Telegram, referencias de reproducción, archivos locales y `fecha_agregado` están protegidos. No asigna nuevas fechas a registros históricos.
4. Si hay un valor anterior verificable para la misma identidad/temporada/episodio/campo, lo repone. Puede usar la base descargada no restringida, o `metadata_undo.before` cuando la identidad y los campos afectados de `after` coinciden. Nunca restaura un valor ya marcado como retirado ni uno de otra ficha.
5. Sin un original verificable, aparta el campo. Si el campo es el título principal obligatorio, usa una etiqueta explícita «Contenido ID · revisar título» para conservar el registro y el enlace sin publicar el nombre restringido. Es una etiqueta operativa, no un título inventado como metadato. Los nombres de episodios y otros campos opcionales pueden quedar sin dato hasta revisarlos.
6. Retira el registro de procedencia obsoleto correspondiente al valor apartado, o repone la procedencia anterior comprobada. No cambia TheTVDB por TMDB/manual para legalizar el mismo dato. Conserva las demás atribuciones y propiedades desconocidas, salvo objetos identificados expresamente como datos restringidos.
7. Conserva un registro privado de incidencias y huellas de los valores identificados. Detecta copias del mismo texto normalizado en otros campos de esa ficha, alias y objetos/listas desconocidos; para textos de al menos 32 caracteres también cruza otras fichas. Los números comunes no se prohíben globalmente. Esto evita un simple cambio de etiqueta o copia de campo como vía de publicación.
8. Una recuperación nueva efectuada por la integración vigente de TMDB/TVmaze puede aportar legítimamente el mismo texto: el repositorio registra una comprobación interna de los campos realmente seleccionados. No basta modificar una etiqueta en un JSON histórico. Esas comprobaciones y huellas pertenecen al estado privado, no al catálogo público.
9. Si falta espacio, falla el archivo de respaldo o falla la escritura atómica, se conserva el estado anterior y se informa el error. Un fallo de archivo no se ignora para publicar datos restringidos. No es el antiguo bloqueo global por proveedor.

El borrador saneado sigue siendo borrador: no se incorpora al catálogo hasta confirmar el guardado habitual. Si la limpieza modifica un registro ya guardado, quedan pendientes para publicar la versión segura. La migración no se ejecuta sobre `collections-state.json`, su respaldo/borrador, ni `collections-tmdb-cache.json`.

### Límites de identificación

No existe un método fiable para atribuir cualquier texto sin procedencia. Si alguien borró previamente todas las marcas, respaldos y huellas, o reescribió el contenido por fuera de Admin, la app no puede demostrar su origen. La limpieza no acusa a todo el catálogo por esa incertidumbre. Las rutas históricas no reconocibles y contradicciones quedan detalladas para revisión; no se adivinan correspondencias ni se eliminan referencias protegidas. Las coincidencias de texto son una protección conservadora, no un detector universal de autoría.

La base remota se trata como copia independiente conforme a la confirmación del propietario y a las marcas disponibles; no se presenta como una auditoría física del contenido remoto. No se recopilan ni envían los valores retirados a Work.

## Credenciales

`RetiredCredentials.remove` elimina exclusivamente `thetvdb-config.enc`, sus archivos auxiliares `.bak`/`.new` y el alias `miflix-admin-thetvdb-v1` de Android Keystore. No descifra ni registra sus valores, no genera otra clave y no abre/borra `admin-config.enc` ni el alias Cloudflare/TMDB. No queda un token persistido: el proveedor que lo mantenía solo en memoria fue eliminado y la actualización reemplaza ese proceso.

Se reintenta al abrir Admin. Un fallo específico de Keystore se informa sin borrar la configuración general ni bloquear la publicación normal. El respaldo de catálogo no incluye los archivos de credenciales. Como todo archivo privado de una app, el respaldo no garantiza confidencialidad frente a un dispositivo comprometido; debe exportarse solo a un lugar privado.

## Publicación con el Worker original

Se conserva `GET /catalogo.json` y `PUT /admin/catalogo` con Bearer existente, schema_version 1 y JSON completo. No hay endpoints nuevos, migración de servidor ni despliegue. No se usa la rama experimental de Worker.

Antes de publicar se vuelve a descargar el remoto y se compara con la base local mediante la huella existente (ignora solo generated_at). Si cambiaron títulos, colecciones remotas o cualquier otra propiedad, no se hace el PUT: se conservan los pendientes y se informa el conflicto. Si coincide, se produce la copia pública saneada y se publica. Solo una confirmación `ok:true` permite actualizar la base al JSON efectivamente enviado, limpiar pendientes y registrar última sincronización. Un error de red conserva trabajo y checkpoints para reintentar.

La copia pública conserva `items`, registros existentes, temporadas/episodios, orden, propiedades desconocidas y `colecciones`/`colecciones_version` remotas si ya estaban presentes. Las colecciones locales siguen en su archivo separado y no se inyectan en el PUT. Los campos locales que ya se excluían del JSON público (`poster_local`, `local_path` de episodios) mantienen su tratamiento anterior.

**Límite del Worker original:** el GET previo no crea una transacción. Otro administrador podría escribir entre esa comprobación y el PUT. No se atribuye atomicidad a KV ni se asegura concurrencia global sin cambiar servidor. Se mantiene la indicación de administrar desde un dispositivo a la vez. Esta corrección elimina el bloqueo TheTVDB y evita sobrescribir un cambio remoto que ya es visible en la comprobación; no implementa sincronización concurrente de colecciones.

## Interfaz y revisión

Lista la ficha, ID estable, nombre anterior si fue necesario apartarlo, temporada/episodio/campo y la acción aplicada. Permite abrir la ficha para completar desde TMDB/TVmaze o datos propios, y exportar cada respaldo privado mediante el selector de documentos Android.

La lista es un historial de limpieza, no un bloqueo ni una prueba de que el campo siga vacío después de editarlo. La ficha muestra el dato actual. Los respaldos exportados son estados privados completos y pueden contener datos retirados y enlaces privados: no son archivos de catálogo publicables. No hay restauración automática que vuelva a introducir esos datos. Una restauración futura por las rutas del repositorio o serializer vuelve a pasar por el saneamiento.
